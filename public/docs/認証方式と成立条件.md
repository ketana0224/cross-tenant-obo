# OBO・個別OAuth・アプリ認証の成立条件

検証した条件と一般的な設定要件を分けて記す。公式資料は[参照一覧](公式資料と参照一覧.md)、結果は各マトリクスを参照する。

## 1. Copilot Studio：カスタムコネクタの本人OBO／SSO

確認した成功構成は **Hの本人 -> Copilot Studio(H) -> OBO有効カスタムコネクタ -> RにホストされたH認証の疑似API**（D03）。

必要な準備と確認：

1. エージェントの本人認証と、ツールのエンドユーザー認証を使用する。確認したツール設定は `authMode: Invoker`。
2. カスタムコネクタのOAuth／Entra設定を下流APIの発行元・宛先・委任スコープと整合させ、OBOを有効にする。確認した設定は `EnableOnbehalfOfLogin=true`。
3. 必要なAPI委任同意と、コネクタクライアントの `access_as_user`／Azure API Connectionsの事前承認を整える。
4. 管理者の準備接続と、実行時の本人所有SSO接続を区別する。
5. 下流が署名・発行元・宛先・本人・委任権限を検証し、本人の操作権限を確認する。

3名で本人所有SSO接続の生成とidentity取得を確認した。すべての人・チャネルで初回サインインや許可要求が省略される保証ではない。内部のトークン交換要求そのものは直接採取していない。

### 利用者追加で省略しない順序

| 順序 | 前提 | 確認方法・注意 |
| --- | --- | --- |
| 1 | 環境グループ所属 | 対象環境の実際のアクセス用セキュリティグループを確認。制限があれば本人の所属と付随ロールを確認し、承認後に必要最小限を追加する。制限なしならその根拠を記録 |
| 2 | Dataverseユーザー登録 | Dataverseがある場合、所属確認後に対象環境への登録済み・有効状態を独立して確認する |
| 3 | 共有・ロール | 必要な最小限のDataverseロール、エージェント利用権限、カスタムコネクタ利用権限を別々に確認する |
| 4 | 本人の追加・初回実行 | Copilotストア等での本人によるエージェント追加を確認。初回OBO／SSO試験を、本人の通常OAuth接続の事前手動作成で代用しない |

Dataverse未登録の場合の導線：Power Platform管理センター -> 管理 -> 環境 -> 対象環境 -> 設定 -> ユーザーとアクセス許可 -> ユーザー -> 「ユーザーの追加」。追加後に一覧更新または管理APIで有効状態を確認する。

グループ追加だけでDataverse登録も完了したと報告しない。ライセンス・アカウント有効状態・グループ所属の不足を、グループ制限解除、組織全体共有、管理者／作成者権限追加で回避しない。他人の接続共有は本人のOBO／SSO接続とは別物である。

## 2. Foundry：native OBO（MCP／A2A）

**Foundryの標準OpenAPIツールは本人OBO非サポート。** 対応する認証方式は匿名、APIキー／事前保存トークン、プロジェクトMIであり、実行した本人のトークンをOBOで引き継ぐ方式ではない。D08・D16は未検証扱いではなく、仕様上の非サポートとして記録する。[公式OpenAPI認証設定](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/tools/openapi)を参照。

以下は、本人OBOを使用するMCP／A2A接続の条件。

| 項目 | 条件 |
| --- | --- |
| 入口 | ソースエージェントの `AgentBlueprint` 方式。本人トークンの `aud` はそのBlueprint、今回の入口スコープは `access_agent` |
| 本人 | 入口テナントの本人として認証。R入口ではRのGuest本人。管理者／MIで本人実行を代用しない |
| 接続 | `authType=AgentOnBehalfOfUser`。MCPは `category=RemoteTool`、A2Aは `category=RemoteA2A` |
| 宛先・スコープ | 下流の実エンドポイントと、1リソースの完全修飾委任スコープ。複数リソースのスコープを混在させない |
| Blueprintの権限 | `requiredResourceAccess` と `inheritablePermissions` に下流の委任権限を記録する。宣言だけでアクセスは付与されない |
| 同意 | 入口クライアントからBlueprint、Blueprint／エージェントから下流への必要な委任同意。今回の検証は本人・対象スコープに限定 |
| 下流 | JWTの署名・期限・`iss`・`tid`・`aud`・`oid`・`scp`を検証し、必要に応じてactor／クライアントも確認。操作・データの本人認可を実施 |

Foundryの実行には対象プロジェクトへの利用権限も必要。検証ではプロジェクト範囲のAgent Consumerを確認した。権限宣言・接続保存・ゲスト招待だけでOBO成功とはしない。

`AgentOnBehalfOfUser` はプレビュー。公式資料の `UserEntraToken` 互換経路とは分ける。本資料の実機成功を、別の入口方式／チャネル／互換方式に拡張しない。

### テナントの整合

- **同じ発行元を受け入れる構成**：R本人 -> Foundry(R) -> R認証下流、H本人 -> Foundry(H) -> H認証下流で成功を確認。
- **ホストが別テナント**：Foundry(H) -> RにホストされたH認証下流でも成功を確認（D17／T17）。
- **登録先が別テナントの追加構成**：MCPではAPIをマルチテナント化し、入口側SP・委任同意・発行元検証・本人認可をそろえて成功（D09-M／D20-M）。
- この追加構成は、入口テナント発行トークンをAPIが受け入れるようにしたもの。OBOで本人を反対側テナントのホーム本人へ切り替えた結果ではない。
- **A2AでのマルチテナントAPI追加構成は未検証**。MCPの成功やA2Aのタイムアウトから、その可否を断定しない。

APIをマルチテナント化しても全テナントを信頼する必要はない。許可する発行元・本人・権限を限定する。

## 3. 個別OAuth

入口とは別に下流用の本人OAuthセッションを確立する方式。

1. 下流の認可／トークンエンドポイント、クライアント、リダイレクトURI、委任スコープ、同意を整える。
2. 本人が下流の認証先へサインインできることを確認する。R認証下流ではRのGuestとしてサインインする場合がある。
3. native許可要求を取得し、本人がサインイン・必要なMFA／許可を完了する。
4. 同じ実行を再開し、下流の実出力と本人を確認する。許可要求の表示だけでは成功ではない。
5. 後続の実行では本人の接続が再利用される場合がある。毎回画面が出ないことはOBOの証拠ではない。

確認済みのMCP／A2AはそれぞれD10・D13・D18・D21、T10・T13・T18・T21。今回のCopilot Studioの別OAuth構成は未検証。

## 4. アプリ認証と認可

- **プロジェクトMI**：自テナント発行のトークンを取得する。下流リソースがその発行元・MI・宛先・アプリ権限を受け入れる必要がある。
- **アプリロール**：APIで公開し、呼び出し元アプリ／MIに割り当てる。下流で `roles` と主体を検証し、実データへの認可も行う。
- **クライアント資格情報**：MIとは別。下流テナント側で準備したアプリ資格情報を使う構成や、中間APIの別資格情報を使う構成を区別する。
- **本人権限**：入口を本人が操作しても、下流がMIで認証していれば本人OBOではない。ユーザー別認可が必要なら別途設計・検証する。

MIと下流の発行元が整合したOpenAPI／MCP（A07・A10）とA2A（T11）で成功を確認。反対テナントの単一テナントAPIを直接呼ぶMI構成はトークン取得等で不成立（A06・A11・T19）。

標準SharePointツールは、検証時に本人認証のみという仕様を確認した。Graphアプリ権限や別資格情報の中間APIへ置換した結果とは分ける。
