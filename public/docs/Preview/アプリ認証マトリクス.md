# アプリ認証・認可のマトリクス

原資料のアプリ認証12構成に `A` を付けて匿名化した。本人委任のD番号、A2AのT番号とは別系列。

入口を本人が操作していても、下流でプロジェクトMIを使う行は**アプリ認証**。条件は[成立条件](認証方式と成立条件.md)、証跡の限界は[検証方法](検証方法と限界.md)を参照する。

○は記載した方式・操作での実機成功。×は実行不成立。`×（仕様）` は標準機能の仕様確認であり、実機拒否の観測ではない。—は構成案または未検証。

疑似APIのアプリ認証には、API用Entraアプリ登録、アプリロールの公開、呼び出し元アプリ／MIへのロール割当が必要。A07・A10ではプロジェクトMIと同じ認証先テナントにAPI用Entraアプリをシングルテナント登録した。Microsoftの標準サービス用アプリを利用者が新規登録する説明ではない。

## 別資格情報の中間API：追加構成A05-R

```text
Foundry(R)
  -> RプロジェクトMI
    -> RでMIを認証する専用中間API
      -> 中間APIがHアプリのclient credentialsを使用
        -> Graph(H)の限定した合成文書
```

**○：OpenAPI・MCPの両方で文書本文取得に成功（2026-11-05）。** 中間APIのログと照合した。H側アプリの読み取りを対象文書1件に限定した。

これはMIがH発行トークンを取得した結果ではない。別資格情報を使う追加の認証境界であり、本人OBOでも標準SharePointツールのアプリ認証でもない。
