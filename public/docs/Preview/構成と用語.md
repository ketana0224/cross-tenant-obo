# 構成と用語

## 2テナントのモデル

| 記号 | 意味 |
| --- | --- |
| H | 利用者のホームテナント。Microsoft 365／Copilot Studio側のEntraテナント |
| R | Hとは別のリソース側Entraテナント。Azureリソース／Foundryを配置した側 |
| 本人H | HのMemberとしての利用者 |
| 本人R | 同じ利用者がRに招待されたGuestとしての利用者 |

HとRは役割を示す匿名ラベルであり、実Tenant IDではない。両方にFoundryを配置した構成を検証している。「Azureテナント」「M365テナント」は別種のID基盤ではなく、どちらもMicrosoft Entra IDテナントである。

同じ人でもHとRの `tid`・`oid` は異なる。本人の対応付けは明示的に確認し、メールアドレスの一致だけで認可しない。

## 別々に記録する境界

```text
本人／入口クライアント
  -> エージェントの入口認証
    -> 接続方式（HTTP/OpenAPI、MCP、A2A）
      -> 下流トークンの発行元・主体・権限
        -> 下流サービスのトークン検証
          -> 操作・データへの認可
```

| 境界 | 確認すること |
| --- | --- |
| ホスト場所 | エージェント／API／A2Aサーバーをどこで稼働させるか |
| アプリ登録先 | 下流リソースアプリをどのテナントで登録したか |
| 入口認証先 | どのテナントの本人／アプリとしてエージェントを実行するか |
| 下流の認証先 | 下流がどの発行元・宛先・主体のトークンを受け入れるか |
| 認可 | 委任スコープ／アプリロールと、その主体の操作・データ権限 |

**ホスト場所やアプリ登録先だけで、受け入れるトークンの発行元は決まらない。**

## 認証方式

| 方式 | 下流の主体 | 区別するポイント |
| --- | --- | --- |
| 本人OBO | 入口の本人に代わって動作するクライアント／エージェント | 個別OAuthセッションやMIを代用しない。Foundryのnative方式は `AgentOnBehalfOfUser` |
| 個別OAuth | 下流用に本人がサインインしたセッション | 入口と同じテナントへの追加サインインでもOBOとは別 |
| アプリ認証 | MI／サービスプリンシパル等 | 本人の委任権限を下流に自動継承しない |
| 匿名負対照 | 認証主体なし | 401は保護動作の確認。本人OBO非対応を示す試験ではない |

本人委任には `scp`、アプリ権限には通常 `roles` を使用する。ただし、APIの実際の発行・認可仕様に従って検証する。アプリロールを付けただけで、すべての業務データにアクセス可能になるわけではない。

## 接続面と対象

- **API**：検証ではHTTP／Foundry標準OpenAPI／Copilot Studioカスタムコネクタ。
- **MCP**：MCPサーバーの実ツール出力を確認。APIをMCPで公開する構成を含む。
- **A2A**：Foundryのnative A2Aツールから専用identity agentを呼ぶ。A2A受信側は0.3系。
- **SharePoint**：元のマトリクスとの対応を残すための参考対象。標準ツール、Graph、自前の中間APIを区別する。
- **疑似API**：合成の本人／アプリ情報を返す。Entra認証とツール実行は実環境だが、実Snowflakeの検証ではない。

A2Aへの置換試験はSharePoint文書取得と等価ではなく、SharePointのライセンス条件もA2Aへ転用しない。
