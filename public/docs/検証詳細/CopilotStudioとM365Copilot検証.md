# Copilot Studio／M365 Copilot：本人SSOとツール認可の検証詳細

対象日：2026-11-01〜02、2026-11-12。[詳細の入口](README.md)／[APIM側の詳細](APIMと外部認可API検証.md)。

## 1. 過去の試験と今回の追加試験を分ける

| 対象 | 確認したこと | その試験だけでは確認していないこと |
| --- | --- | --- |
| 11月1〜2日の利用者報告 | 本人情報、権限内データ取得、権限外403の報告 | 実ツール履歴全体とAPIログの独立照合 |
| コネクタ単体・管理者プレビュー | コネクタテストや実ツール履歴で取得・拒否を確認 | 公開チャネルでの別利用者の初回SSO |
| D03：カスタムコネクタOBO／SSO | 3名の本人所有SSO接続の新規生成とidentity取得を照合 | 現行D03でのデータ取得・権限外拒否 |
| P04〜P06：11月12日の専用MCP構成 | APIM・外部認可API経由でread許可・write拒否、一般利用者の初回SSO | D03の未検証データ操作や、他チャネルの初回SSO |

後日の専用MCP試験を理由に、過去のHTTP構成の未検証項目を成功へ書き換えない。

## 2. 11月12日の経路

```text
利用者
  → 専用Copilot Studioエージェント
  → OBO有効のMCPカスタムコネクタ（Invoker）
  → API向け本人委任トークン
  → APIMでJWT検証
  → 外部認可APIで本人・client・ツール別判定
      ├─ read許可 → 合成MCPバックエンド
      └─ write拒否 → APIMで403、バックエンドを呼ばない
```

保存済みコネクタ定義のOBO有効設定と、Dataverse上の実MCPコンポーネントの`connectionProperties.mode: Invoker`を確認した。M365のサインイントークン、IDトークン、Graph用トークンをそのままAPIMへ送った試験ではない。

## 3. 共有・接続より前に確認した利用者準備

環境・グループ・利用者の実名やIDは公開しない。以下は試験時に確認した状態であり、他環境の既定値ではない。

| 順序 | 独立した確認項目 | 実施状態・根拠 |
| --- | --- | --- |
| 1 | 環境グループ所属 | 確認済み。対象環境のアクセスグループを実確認し、管理者・一般利用者とも既存所属。グループ追加・制限解除なし |
| 2 | Dataverseユーザー登録 | 確認済み。両者が対象環境に登録済み・有効。グループ所属だけで登録完了とは判断しない |
| 3 | 利用者ロール | 確認済み。一般利用者は既存Basic User。管理者／Makerロール追加なし |
| 4 | エージェント共有 | 本人に利用権限のみ。編集・分析権限や組織全体共有なし |
| 5 | コネクタ共有 | 本人にCan view。管理者の接続そのものは共有しない |
| 6 | 本人によるエージェント追加 | M365で本人が追加。管理者の公開／共有とは別に実施 |
| 7 | OAuth同意 | `Probe.Read`を対象2名のPrincipal同意に限定。組織全体同意なし |

未所属・未登録の利用者を準備する場合は、[利用者追加の正規手順](../Preview/認証方式と成立条件.md#利用者追加で省略しない順序)に従い、権限影響の確認と承認後に本人だけを追加する。通常OAuth接続の事前手動作成で、初回OBO／SSOの試験を置き換えない。

## 4. 管理者の準備接続と一般利用者の初回SSO

| 主体 | 接続と実行の観測 | 結論 |
| --- | --- | --- |
| 管理者 | 通常OAuthの準備接続を先に作成。`isSsoConnection=false` | 管理者read成功だけでは手動接続不要SSOの実証にならない |
| 一般利用者 | 通常OAuth接続を手動作成せず、本人所有・`Connected`・`isSsoConnection=true`の接続が新規生成 | このM365 Copilot試行で本人SSOを確認 |

一般利用者の最終readでは、APIMで検証された`oid`が本人、`tid`が対象テナント、`aud`が検証API、`scp`が`Probe.Read`、`azp`が専用コネクタクライアントであることを照合した。管理者接続の流用ではない。

OBO／SSOでも初回サインインや許可要求が一切出ないという保証ではない。内部のトークン交換要求そのものを直接採取したわけでもない。

## 5. P04〜P06：最終結果

| 公開ID | チャネル・主体 | read | write |
| --- | --- | --- | --- |
| P04 | Copilot Studio・管理者 | 許可、対応するバックエンド実行1件 | 認可拒否、対応するバックエンド実行0件 |
| P05 | M365 Copilot・管理者 | 許可、対応するバックエンド実行1件 | 認可拒否、対応するバックエンド実行0件 |
| P06 | M365 Copilot・一般利用者 | 最終修正後に許可、本人UIと対応するバックエンド実行1件 | 認可拒否、対応するバックエンド実行0件 |

一般利用者では初期化・一覧の認可許可とバックエンド到達も確認した。本人UI応答と、独立した認可・バックエンド監査のclaims、相関関係、認可往復時間を照合した。

「1件」は対応する要求相関ID単位。一般利用者の収集監査には別のread要求も1件あり、その起点は独立確認できていない。会話全体でreadが1回だけだったとは断定しない。管理者M365でも許可直後の先行readは明示的read試験のbaselineから除外しており、ツール未実行の対照試験ではない。

write画面には`Tool did not respond with success`という汎用エラーが出た。画面だけで403や拒否理由を確定せず、認可監査とバックエンド未実行を照合した。

## 6. 一般利用者の失敗から最終成功まで

| 段階 | 観測 | 確認できた原因・修正 |
| --- | --- | --- |
| 初期試行 | 接続許可後の汎用エラー、本人接続・認可監査0件 | この段階の直接原因は未確定。認可拒否とも断定しない |
| 本人SSO成立後 | 本人のAPI向けトークン到着、`initialize`拒否 | 認可APIの本人条件が管理者限定。tenant・audience・API・scope等は一致し、本人OIDだけ不一致 |
| 認可APIだけ修正した途中版 | 認可APIは許可、MCP側が`forwarded_claims_mismatch`で拒否 | MCPバックエンドにも管理者限定チェックが残っていた |
| 最終修正後 | 初期化・一覧・read成功、write拒否 | 両側の本人チェックを共通化し、一般利用者本人OIDと専用clientの組み合わせだけ追加許可 |

再公開だけで解消した問題ではなく、認可APIとバックエンドの条件不整合を修正した結果。一般利用者の環境管理者化・組織全体への許可・JWT検証の解除で回避したものではない。

認可APIの12ケースとMCP側9ケースの設定確認も行ったが、専用キーを使う合成診断であり、本人トークンによるM365実行の証拠には数えない。最終の関連単体テスト記録は25件成功で、過去段階との加算はしない。

管理者の準備接続では`AADSTS7000215`も観測した。専用コネクタのシークレット値を利用者が直接再設定・保存して接続作成に成功した。秘密値は公開資料に含めない。
