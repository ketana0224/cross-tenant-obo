# 再検証手順と記録項目

本書は追試時のチェックリストであり、実環境にそのまま投入するスクリプトや完全なデプロイパッケージではない。公開整理に伴う実機再実行も行っていない。[詳細の入口](README.md)。

## 1. 元条件と変更点を固定する

最初に対象IDと[統合結果](../検証結果統合マトリクス.md)を選び、次を別々に記録する。

| 項目 | 記録例（すべて匿名ラベル） |
| --- | --- |
| 対象・比較元 | D09、条件変更後D09-M、P03等 |
| 検証日時・版 | 日付・タイムゾーン、SDK／APIバージョン、ツール／プロトコル版 |
| エージェント入口 | Foundry／CS、入口テナント、本人Member／Guest、入口クライアント |
| 下流 | ホスト場所、APIアプリ登録先、単一／マルチテナント |
| 下流認証 | 受け入れる発行元、audience、OBO／OAuth／MI、scope／role |
| 実行主体 | 管理者準備／本人実行、期待する本人またはアプリ |
| 操作・期待値 | identity／read／write、許可／拒否、障害時未転送 |
| 前回との差 | SP・同意・発行元・本人認可・接続・コードの変更箇所 |

実ID・同意URL・資格情報は非公開側で管理する。公開する設定例に実値を一度埋めてから消す運用を避ける。

## 2. 利用者の準備

### Power Platform／Dataverseを使う場合

必ず共有・接続作成より先に、以下を順に確認する。

1. **環境グループ所属**：対象テナント・環境のアクセス用セキュリティグループを実確認。制限があれば本人の所属と付随ロールを確認し、変更承認後に本人だけを追加、反映を確認する。制限がなければ「確認不要：対象環境にグループ制限なし」と根拠を記録し、新規グループは作らない。
2. **Dataverseユーザー登録**：Dataverseがあれば、上記確認後に対象環境のユーザー登録済み・有効状態を独立確認。未登録ならPower Platform管理センター → 管理 → 環境 → 対象環境 → 設定 → ユーザーとアクセス許可 → ユーザー →「ユーザーの追加」。本人を追加後に一覧更新または管理APIで反映を確認する。
3. 追加できない場合は表示されたライセンス・アカウント有効状態・環境グループ所属の不足条件を確認する。グループ制限解除や管理者／Maker権限追加で回避しない。
4. 必要最小限のロール、エージェント利用権限、コネクタ利用権限を別々に確認する。他人の接続の共有と混同しない。
5. 管理者の共有・公開とは別に、本人がCopilotストア等でエージェントを追加したことを確認する。
6. 初回OBO／SSOなら、本人の通常OAuth接続を先に手動作成しない。管理者準備接続・既存本人接続・新規本人SSO接続・初回許可要求を区別して記録する。

### Foundry単独の場合

- 環境グループ所属：**確認不要：Power Platform環境を使用しない**。
- Dataverseユーザー登録：**確認不要：Dataverseを使用しない**。
- これらとは別に対象Foundryプロジェクトの利用権限を確認する。管理者実行やMIで本人試験を代用しない。

## 3. 認証設定を準備する

| 方式 | 最低限確認する設定 |
| --- | --- |
| Foundry native OBO | APIアプリと委任スコープ、Blueprint入口、`AgentOnBehalfOfUser`、完全修飾スコープ、Blueprintの権限宣言・継承、必要な本人限定同意 |
| 個別OAuth | APIとOAuthクライアント、下流テナントの認可先、リダイレクトURI、同意、本人サインイン後の同一実行の再開 |
| プロジェクトMI | APIのaudience、MIの識別、アプリロール公開・割当、受信側のアプリ認可 |
| CSの本人OBO／SSO | OBO有効コネクタ、Invokerモード、本人所有接続、API委任権限・必要な同意 |
| APIM＋外部認可 | JWT検証、検証済みclaims抽出、MCP対象抽出、認可APIの認証、応答型・相関確認、拒否／障害時の未転送 |

受信側のJWT署名・期限・発行元・宛先の検証を省略しない。複数テナント構成ではAPI登録のマルチテナント化だけでなく、入口テナントのSP・委任同意・受信側の発行元検証・本人認可を確認する。

詳細は[成立条件](../Preview/認証方式と成立条件.md)。[接続テンプレート](../../examples/README.md)は概念例であり、必要なアプリ登録・入口・同意を作成するものではない。

## 4. 実行して層ごとに照合する

1. 本人が想定テナントにサインインする。秘密値・認可コード・トークン本体・認証キャッシュは公開成果物に保存しない。
2. 入口の検証済み`tid`・`oid`・`aud`・呼び出し元・`scp`を確認する。未検証JWTのデコードだけを証拠にしない。
3. ネイティブツールを明示実行する。OAuth許可が必要なら本人操作後に同じ実行を再開する。
4. HTTPコードと別に、call/output、完了状態、`isError`、実出力の主体・権限を確認する。生成文章を代用しない。
5. 受信側ログが取得できる場合、同じ実行・要求との相関、検証済み主体、対象操作を照合する。A2Aでは受信側生成receiptとnative出力を照合する。
6. APIM外部認可では、認可判断だけでなく、許可後の対象バックエンド実行と拒否／障害時の0件を相関ID単位で照合する。分単位メトリックやUIだけで確定しない。
7. 再試行、探索、初期化、先行readを明示操作と分ける。相関できない追加実行は件数から黙って除外せず、不明として記録する。

## 5. 最低限の対照試験

以下は追試計画のチェックリストであり、すべてを今回実施済みという意味ではない。実施記録がないケースは未検証とする。

| ケース | 期待値・確認点 |
| --- | --- |
| 想定本人の権限内操作 | 実ツール出力と受信側の主体が一致 |
| 想定本人の権限外操作 | 拒否。APIM構成なら対象バックエンド未実行も確認 |
| 無認証・宛先不一致 | 拒否。匿名401を本人OBO不成立とはしない |
| 発行元・本人条件を変えた比較 | 元条件と変更条件を別ケース化。成功のために条件を変えたなら明示 |
| 認可APIの障害 | 許可へフォールバックせず、対象バックエンド未転送 |
| 認可APIの期限超過 | 期限・実待機条件・各層の応答コードを記録 |
| 認可APIの不正な許可応答 | 文字列のtrue等を許可扱いしない |

## 6. 判定と公開用の記録雛形

**成功**はその方式・操作・構成に限定する。期待した拒否は「拒否確認」と明示。不成立・仕様上の非対応・未検証・利用者報告を別分類にする。

| 記録欄 | 記入する内容 |
| --- | --- |
| 対象ID・検証日 | 比較元、変更後条件、日付・タイムゾーン |
| 環境グループ所属 | 実施済み／未実施／確認不要、その根拠 |
| Dataverseユーザー登録 | 実施済み／未実施／確認不要、その根拠 |
| 前提・変更 | 利用者ロール、共有、同意、認証設定、前回からの変更 |
| 期待値 | 許可／拒否、本人／アプリ、対象操作 |
| 観測 | 各層HTTP、native出力、検証済みclaimsの匿名比較、バックエンド到達 |
| 証跡の範囲 | UIのみ／実ツール出力／受信ログ照合、未取得の証跡 |
| 判定 | 成功／拒否確認／不成立／仕様／未検証／利用者報告 |
| 原因と限界 | 確定事項、推測、未解消事項を分離 |
| 回帰範囲 | 修正後に再実行したケース、過去結果を参照するだけのケース |
| 後処理 | 一時サーバー・監査収集の停止、秘密の処理、残置リソースと承認 |

## 7. 公開前

原本は非公開に保持し、公開ID単位の匿名要約を作成する。実UPN・個人名・リソース名・URL・各種ID・秘密・同意URLを除き、公開ファイルだけでリンクが完結することを確認する。

詳細レポートを追加しただけで実機結果の現行性やGitHub公開完了を報告しない。[公開ポリシー](../Preview/公開と非公開のポリシー.md)に従い、許可リスト、追跡対象、ステージ済み内容、公開予定のブランチ・タグ・履歴を確認してから公開する。
