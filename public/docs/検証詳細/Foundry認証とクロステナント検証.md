# Foundry：認証方式とクロステナント検証の詳細

検証期間：2026-11-03〜2026-11-11。[詳細の入口](README.md)／[統合結果](../検証結果統合マトリクス.md)。

## 1. 検証した境界

M365は利用者のホームテナント、Azureは別のリソース側テナントを示す。Azure入口では同じ利用者のゲストIDを使う。ホスト場所、APIアプリの登録先、トークンの発行元を別々に記録した。

```text
利用者 → Blueprint宛ての入口トークン → Foundry
  ├─ 本人OBO：AgentOnBehalfOfUser → API宛ての委任トークン
  ├─ 個別OAuth：下流用に別サインイン → API宛ての本人トークン
  └─ プロジェクトMI → API宛てのアプリトークン
      → MCP／HTTP API／A2Aの認証・操作認可 → 実ツール出力
```

下流に見える主体が本人なのかアプリなのかを検証し、生成回答だけで成功にしなかった。接続保存、ゲスト招待、同意の設定完了も実行成功とは別に扱った。

## 2. native MCPの本人OBO

### 準備した設定

1. 下流API用Entraアプリに委任スコープを公開する。基本構成は下流認証先への単一テナント登録。
2. Foundry入口を`AgentBlueprint`にし、本人トークンの`aud`を対象Blueprint、`scp`を`access_agent`に整合させる。
3. 接続を`category=RemoteTool`・`authType=AgentOnBehalfOfUser`とし、対象APIの完全修飾委任スコープを指定する。
4. Blueprintの`requiredResourceAccess`・`inheritablePermissions`と、入口／下流に必要な本人限定同意を準備する。権限の宣言だけで同意完了とはしない。
5. 下流が署名・期限・発行元・`tid`・`aud`・`oid`・`scp`を検証し、本人の操作を認可する。

クライアントから下流用トークンを注入せず、Foundryによるnative呼び出しを実行した。Entraのトークン交換通信そのものをすべて採取したわけではない。

### 11月11日：M365発行固定の追加検証

同じAzureゲスト入口・エージェント・OBO接続で、専用MCPの受理条件を切り替えて比較した。

| 段階 | MCPの受理条件 | 結果 |
| --- | --- | --- |
| 最初 | M365発行・M365本人 | Foundry HTTP 400。MCPで`InvalidIssuerError` |
| 対照 | Azure発行・Azureゲスト本人へ変更 | HTTP 200、実identityツール1回完了。MCPの署名検証済み`tid`・`oid`がAzureゲスト本人 |
| 復元後 | M365発行・M365本人へ戻す | 再びHTTP 400、MCPで`InvalidIssuerError` |

この結果は、下流認証先を変えれば成功したという対照であり、**M365発行固定の成功ではない**。初期D09のタイムアウト原因まで、この別試験だけで確定したとも扱わない。

対照試験では、汎用判定器が既定の`server_label`と一致しないため`success=false`を返した。実ツール出力と受信側の検証ログを照合して対照成功と判断した。集約フラグを無条件に採用せず、不一致理由も記録した。

## 3. M365本人からAzure Foundryへの入口

マルチテナントBlueprint、M365側Principal、本人限定同意、入口の許可条件を整備した構成で、Azureゲストサインインを使わないM365本人の入口認証は成功した。同じ本人トークンでM365を許可対象から外すと401、許可を戻すと正常応答になった。

ただし、**入口成功とM365向け下流OBO成功は別**。

- 既存構成の下流OBOはFIC issuer照合エラー`AADSTS7002111`で不成立。
- 専用構成ではM365側Agent Identityの作成まで確認した。
- `instance_identity`は読み取り専用で、RESTで指定しても保存後はAzure側IDのままだった。手動差し替えは不成立。
- 追加native OBOもHTTP 400。入口認証の成功を下流成功へ読み替えない。

## 4. 個別OAuthとの比較

D10・D18では下流用M365サインイン、D13・D21では下流用Azureサインイン後に実MCPの本人情報取得を確認した。D21の下流ではAzureゲスト本人を使い、APIの単一テナント登録は保持した。

OAuth許可要求が出ただけでは成功にせず、本人の認証・必要な許可後に同じ実行を再開し、実ツール出力を確認した。既存接続の再利用で許可画面が出ない試行もあり、画面が出ないことをOBOの証拠にはしない。

## 5. プロジェクトMI・標準ツール

| 対象 | 観測 | 留保 |
| --- | --- | --- |
| A07：Azure MI → Azure認証API | OpenAPI・MCPで成功。アプリロール割当・アプリ対応付け・実出力・APIログを確認 | 本人権限の継承ではない |
| A10：M365 MI → M365認証API（Azureホスト） | OpenAPI・MCPで成功。実出力・保存接続・MI対応付け・アプリロールを確認 | リクエスト単位のAPI認証ログ照合は未実施 |
| A06・A11：MIと異なる認証先の単一テナントAPI | OpenAPIは接続解決、MCPはARA BadRequestで停止 | 下流APIの401／403を直接観測した結果ではない |
| A05：Azure MI → M365 Graph直接 | Graph 404、本文未取得 | 不存在とテナント固有の拒否を区別できない |
| A05-R：Azure MI → 中間API → 別のM365アプリ資格情報 → Graph | OpenAPI・MCPで対象の合成文書本文を取得し、中間APIログと照合 | M365側の対象文書1件に限定。MIがM365トークンを得たのではない |

標準OpenAPIの本人OBOと標準SharePointツールのアプリ認証は、検証時の仕様上の非対応として整理した。匿名401や独自MCPへの置換で、その標準機能を実証したとはしない。

標準SharePointツールでは、Foundry(M365)から同一テナントのMember本人で、合成文書の未知の検証コード・実ツール出力・出典の一致を確認した。Azureゲスト本人はライセンス／プラン状態を確認しても403、別テナントの文書はHTTP 200でも0件で目的未達だった。他利用者への拒否や網羅的な権限トリミングは未検証。

## 6. A2Aとの比較

11月9日は`a2a_preview`とA2A 0.3系の専用identity agentを使用した。接続は`RemoteA2A`。本人OBOは`AgentOnBehalfOfUser`、個別OAuthは`OAuth2`、MIは`ProjectManagedIdentity`で分けた。

| 分類 | ケース | 観測 |
| --- | --- | --- |
| 本人OBO成功 | T12・T14・T15・T17 | native call/output、期待する本人・委任権限、同じ実行の受信側receipt・ログ、最終応答を照合 |
| 個別OAuth成功 | T10・T13・T18・T21 | 下流用サインイン後の本人受信と最終応答を照合 |
| MI成功 | T11 | プロジェクトMI・アプリ権限・最終応答を照合 |
| 実行不成立 | T07・T09・T20・T22 | SendMessageタイムアウト。本人受信未確認 |
| 実行不成立 | T19 | ARA BadRequest。MI受信未確認 |
| 匿名負対照 | T08・T16 | 受信側401、Foundry側400。本人OBOの可否判定対象外 |

初期試行にはモデル429による最終応答未完了があり、容量変更後に対象構成を再実行した。受信だけの確認を完了成功にはしなかった。OAuthリンクの固定メッセージ接頭辞の処理も修正し、HTTPS・許可ドメインを確認して認証を継続した。

MCPと同条件で比較できた10構成は成否が一致したが、失敗原因の同一性までは意味しない。A2AのAPIマルチテナント追加構成、A2A 1.0の`a2a`ツール、実SharePointへの置換、実Snowflakeへの適用は未検証。
