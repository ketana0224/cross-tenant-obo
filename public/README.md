# マルチテナントのエージェント連携：公開資料

## 目的

Copilot Studio と Microsoft Foundry について、次を分けて成立・非成立パターンを明確にする。

- 認証方式：本人OBO、呼び出し先への個別OAuthログイン、アプリ認証（プロジェクトMI等）。
- 接続方式：API（HTTP／OpenAPI）、MCP、A2A。
- テナント：ユーザーの所属先、エージェント利用のログイン先、呼び出し先の認証先、認証用Entraアプリの登録先、サーバーの配置先。
- 認可：API／MCP／A2Aサーバーが、ユーザーまたはアプリにどの操作・データへのアクセスを許可するか。

## 確認済み範囲の早見表

**「API」列はHTTP／標準OpenAPIによる呼び出しを指す。** MCP／A2A経由のAPI呼び出しが成功しても、HTTP／標準OpenAPIによる呼び出しの成功には数えない。

**「認証先テナント」は、ユーザーやアプリの認証に使うEntraテナントを指す。サーバーの配置先や認証用Entraアプリの登録先とは区別する。** 受信側のサーバーは、認証先テナントが発行したトークンを検証する。

**今回のFoundry基本構成では、API／MCP／A2Aサーバーの認証用Entraアプリを、サーバーの認証先テナントにシングルテナント登録した。** MCPのD09-M・D20-Mだけは、認証用Entraアプリの登録先とは別のテナントから利用するため、マルチテナント登録にした。アプリ登録は両方の構成で必要であり、接続設定や同意だけでは代用できない。

**Foundryの本人OBOは、エージェントがユーザーに代わってMCPサーバー／A2Aサーバーへアクセスする方式である。** Foundryの認証基盤がEntra IDへトークン交換を要求し、Entra IDがMCPサーバー／A2Aサーバー向けの本人トークンを発行する。Foundryの接続機能が本人トークンを呼び出し要求に付加する。エージェント向けの本人トークンをMCPサーバー／A2Aサーバーへ直接転送するわけではない。

**MCP列では、Entra IDが発行したトークンをMCPサーバーが検証し、MCPサーバーの認可ロジックが操作・データへのアクセス可否を判断する。** 今回の検証では疑似API自体がMCPエンドポイントを提供している。MCPサーバーがさらに別のバックエンドAPIを呼ぶ場合、MCPサーバーからバックエンドAPIへの認証・認可は別途必要であり、MCP列の○に自動的には含まれない。

**A2A列では、Entra IDが発行したトークンをA2Aサーバーが検証し、A2Aサーバーの認可ロジックが操作・データへのアクセス可否を判断する。** A2Aプロトコル自体がEntra認証や業務データの認可ルールを定めるわけではない。

**早見表の○は、記載した検証構成での成功であり、すべての構成の対応保証ではない。** 詳細マトリクスの失敗例・未検証範囲も併せて読む。Copilot StudioのMCP／A2Aは未検証であり、製品非サポートと判断したわけではない。

## 重要な結果

- サーバーの配置先が別テナントでも、呼び出し先の認証先テナントと本人／アプリの権限をそろえて成功した構成がある。
- ユーザーを別テナントへゲスト招待しても、OBOでゲスト本人が所属元テナントの本人へ自動的に切り替わるわけではない。
- MCP追加構成では、MCPサーバーの認証用Entraアプリのマルチテナント化、ユーザーのログイン先テナントのサービスプリンシパル、委任同意、MCPサーバー側の本人確認・アクセス許可をそろえて成功した。A2Aの同じ追加構成は未検証。
- 個別OAuthとMIの成功は本人OBOの成功ではない。
- A2Aの最新16構成は、○9件（本人OBO4・個別OAuth4・MI1）、×5件、本人OBO判定対象外の匿名負対照2件。

## 公開範囲

検証期間は2026-11-02〜2026-11-09。原本を保持したまま、個人名・UPN・テナント／アプリ／リソースID・実エンドポイント・秘密・同意URLを含めず、新しい資料に再構成した。

公開資料は匿名化要約であり、原本ログやスクリーンショットを公開していない。独立した第三者による再現完了、実Snowflake、標準Snowflakeコネクタ、本番運用、すべてのデータ認可の検証を意味しない。設定例は概念テンプレートであり、既存環境をデプロイするスクリプトではない。
