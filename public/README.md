# マルチテナントのエージェント連携：公開資料

## 目的

Copilot Studio と Microsoft Foundry について、次を分けて成立・非成立パターンを明確にする。

- 認証方式：本人OBO、下流用の個別OAuth、アプリ認証（プロジェクトMI等）。
- 接続面：API（HTTP／OpenAPI）、MCP、A2A。
- 境界：利用者のホームテナント、入口認証、APIの登録先、ホスト場所、下流が受け入れる発行元。
- 認可：本人の委任スコープとデータ権限、アプリロールとアプリのデータ権限。

**Foundryの本人OBOは、エージェントによる、ユーザーの代理アクセスを意味する。** エージェントがユーザーに代わってMCPサーバー／A2Aサーバーを呼び出す。Foundryの認証基盤がEntra IDにOBOのトークン交換を要求し、Entra IDがMCPサーバー／A2Aサーバー向けの本人トークンを発行する。エージェントは呼び出し先向けの本人トークンを使用する。エージェント向けの本人トークンを呼び出し先へ直接転送するわけではない。

**MCP列では、Entra IDが発行したトークンをMCPサーバーが検証し、MCPサーバーの認可ロジックが操作・データへのアクセス可否を判断する。** 今回の検証では疑似API自体がMCPエンドポイントを提供している。MCPサーバーがさらに別のバックエンドAPIを呼ぶ場合、MCPサーバーからバックエンドAPIへの認証・認可は別途必要であり、MCP列の○に自動的には含まれない。

**A2A列では、Entra IDが発行したトークンをA2Aサーバーが検証し、A2Aサーバーの認可ロジックが操作・データへのアクセス可否を判断する。** A2Aプロトコル自体がEntra認証や業務データの認可ルールを定めるわけではない。

これは**全構成の対応保証ではない**。テナント・権限・プロトコルを含む各行の条件と、失敗行も併せて読む。Copilot Studio のMCP／A2Aが製品として非対応という意味ではない。

## 重要な結果

- ホストが別テナントでも、受け入れる発行元・本人／アプリ・権限が整合すれば成功した構成がある。
- ゲスト招待だけで、OBOが別テナントのホーム本人へ自動的に切り替わるわけではない。
- APIをマルチテナント化したMCP追加構成では、入口側SP・委任同意・APIの検証／認可もそろえて成功した。A2Aの同じ追加構成は未検証。
- 個別OAuthとMIの成功は本人OBOの成功ではない。
- A2Aの最新16構成は、○9件（本人OBO4・個別OAuth4・MI1）、×5件、本人OBO判定対象外の匿名負対照2件。

## 公開範囲

検証期間は2026-11-02〜2026-11-09。原本を保持したまま、個人名・UPN・テナント／アプリ／リソースID・実エンドポイント・秘密・同意URLを含めず、新しい資料に再構成した。

公開資料は匿名化要約であり、原本ログやスクリーンショットを公開していない。独立した第三者による再現完了、実Snowflake、標準Snowflakeコネクタ、本番運用、すべてのデータ認可の検証を意味しない。設定例は概念テンプレートであり、既存環境をデプロイするスクリプトではない。
