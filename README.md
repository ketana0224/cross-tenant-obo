# cross-tenant-obo

Microsoft Foundryを中心に、**本人OBOとアプリ認証・マネージドID（MI）の基本、クロステナント構成、検証結果**をまとめた公開資料です。

**M365＝利用者ユーザーIDが登録されているテナント、Azure＝それとは別のAzureリソース側テナント**。

## 認証・認可が成立する基本ルール

**トークンの発行元テナントが、呼び出し先の認証先テナントと一致し、必要な権限があること。**

Foundryを例にすると、トークンを発行するテナントは次のとおりです。

| 認証方式 | トークンを発行するテナント |
| --- | --- |
| OBO | 利用者がFoundryへサインインしたテナント。ゲストの場合は招待先のテナント |
| アプリ認証（MI） | MIが所属するテナント。FoundryのプロジェクトMIは、そのプロジェクトのテナント |
| アプリ認証（シークレット・証明書） | トークン取得時に指定するテナント。そのテナントに呼び出し元アプリのサービスプリンシパルが必要 |
| (参考)個別OAuth | 利用者が呼び出し先用に別途サインインしたテナント |

発行元テナントの一致だけでは十分ではありません。トークンの宛先が呼び出し先に合っており、必要な権限付与・同意が行われ、下流が本人またはアプリの操作を許可する必要があります。サーバーの配置先やアプリの登録先が、トークンの発行元テナントと同じである必要はありません。

### クロステナント構成

M365の利用者が、別のAzureテナントに配置されたFoundryを利用する構成を、Azure側へのゲスト登録の有無と下流の認証方式で分けます。

| 認証方式 | ゲストユーザー | 非ゲストユーザー |
| --- | --- | --- |
| 本人OBO | [クロステナントOBO-ゲストユーザー](public/docs/クロステナントOBO-ゲストユーザー.md) | [クロステナントOBO-非ゲストユーザー](public/docs/クロステナントOBO-非ゲストユーザー.md) |
| アプリ認証・MI | [クロステナントアプリ認証とMI-ゲストユーザー](public/docs/クロステナントアプリ認証とMI-ゲストユーザー.md) | [クロステナントアプリ認証とMI-非ゲストユーザー](public/docs/クロステナントアプリ認証とMI-非ゲストユーザー.md) |

非ゲスト版は、Azure側に本人を登録せず、Azure認証の入口へ本人が直接アクセスする前提での制約を説明します。非ゲストのすべての構成が不成立という意味ではありません。

### 検証結果

[検証結果統合マトリクス](public/docs/検証結果統合マトリクス.md)に、MCP・A2A・SharePoint・入口認証・HTTP／OpenAPI・カスタムコネクタの結果を、製品・配置・認証方式ごとに掲載しています。

- Foundry(Azure)・Foundry(M365)の結果を分け、成功・不成立・仕様上の非対応・未検証を区別しています。
- Copilot Studio・コネクタ単体の表は参考情報です。
- 「結果・条件・確認範囲」「検証日・出典」は検証時のメモであり、参考情報としてのみ使用します。

検証期間：**2026-11-01〜2026-11-09**。結果は検証時点のものであり、現在の設定・資格情報の有効性や、すべての構成での動作を保証しません。
